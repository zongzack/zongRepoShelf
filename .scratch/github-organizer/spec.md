# GitHub 项目整理工具规格

## Problem Statement

用户的 GitHub 中积累了大量已 Star 的项目和本人拥有的仓库，其中一部分已经停止维护、被 archived/deprecated，或长期没有 release、Issue/PR 活动。用户目前只能手工逐个查看和整理，耗时很长，也难以记住每个项目为什么保留或应该执行什么动作。

问题的核心不是缺少 GitHub 数据，而是缺少一个可以把数据转成“可比较的扫描证据”，再让用户安全批量确认整理动作的工作流。

## Solution

构建一个运行在用户自己电脑上的本地 Web 工具。用户通过命令行启动服务，在浏览器中手动开始扫描；工具复用本机已登录的 GitHub CLI（`gh`）读取当前用户的 Star、owned/fork 仓库、健康信号和 GitHub Lists，并将结果呈现为批量表格；点击列表行后通过 Dialog 查看项目详情。

工具根据可解释的健康信号生成整理建议，但不自动替用户做决定。用户可以从列表行直接展示的动作按钮或批量操作栏发起取消 Star、归类/移出 List、Archive/Unarchive；所有动作都先预览再确认。删除本人拥有的仓库/fork 仅在详情 Dialog 的危险区域提供。所有写操作逐项记录成功/失败；删除等危险动作必须经过额外护栏。扫描结果、List 规则和审计记录保存在单个本地 JSON 文件中，不保存 GitHub Token。

## User Stories

1. 作为个人 GitHub 用户，我想通过一个命令启动本地整理工具，以便不需要部署服务器就能开始整理。
2. 作为用户，我想在浏览器中看到一个清晰的批量整理工作区，以便一次比较多个项目条目。
3. 作为用户，我想显式点击“开始扫描”，以便控制 GitHub API 请求的发生时机。
4. 作为用户，我想复用本机 `gh` 登录状态，以便不必在应用中再次输入或保存 Token。
5. 作为用户，我想在未安装或未登录 `gh` 时看到明确的修复引导，以便知道为什么暂时不能扫描或写回 GitHub。
6. 作为用户，我想扫描当前已 Star 的仓库，以便找到长期积累但可能已经失效的关注项目。
7. 作为用户，我想扫描本人拥有的仓库，包括 fork，以便同时审阅自己的项目维护状态。
8. 作为用户，我不希望工具默认扫描 Watch/Following 列表，以便控制首版范围和权限复杂度。
9. 作为用户，我想看到仓库是否 archived、disabled 或明确 deprecated，以便快速识别维护状态已经终止的项目。
10. 作为用户，我想看到最近一次 commit 时间，以便识别长期没有代码变化的项目。
11. 作为用户，我想看到最近一次 release 时间，以便区分“仍有提交但长期不发布”的项目。
12. 作为用户，我想看到近期 issue/PR 活动，以便判断项目是否仍有协作维护。
13. 作为用户，我想使用默认的 12 个月无 commit、18 个月无 release、6 个月无 Issue/PR 活动阈值，以便快速开始扫描。
14. 作为用户，我想在页面上调整这些阈值，以便根据不同项目类型采用适合自己的判断标准。
15. 作为用户，我想看到每条建议命中的具体证据，以便理解建议来源，而不是面对不可解释的分数。
16. 作为用户，我想让 archived/deprecated 只提高提示优先级，而不自动取消 Star，以便保留我对资料价值的最终判断。
17. 作为用户，我想默认只查看命中至少一项健康信号的项目，以便先处理最值得关注的条目。
18. 作为用户，我想切换到全部项目视图，以便在需要时检查未命中规则的条目。
19. 作为用户，我想通过 `owner/repo` 搜索项目，以便快速定位特定仓库。
20. 作为用户，我想按健康信号、Star/Owned/Fork 关系和 Lists 筛选项目，以便缩小批量操作范围。
21. 作为用户，我想在表格中看到项目条目、健康信号、最近 commit、Lists 和关系摘要，以便快速比较多个项目。
22. 作为用户，我想点击项目列表行后在 Dialog 中查看完整证据，以便不离开批量上下文就能做决定。
23. 作为用户，我想从详情面板查看项目已有的 GitHub Lists，以便避免重复添加或误移除分类。
24. 作为用户，我想从项目行的“操作”菜单取消 Star，以便移除不再关注的项目。
25. 作为用户，我想从项目行的“操作”菜单把项目归类到一个 GitHub List，以便按主题或用途组织 Star 项目。
26. 作为用户，我想把项目从某个 GitHub List 移出，以便修正过时分类。
27. 作为用户，我不希望一个项目同时出现在多个 Lists，以便保持分类互斥且容易查找。
28. 作为用户，我想在更换项目归类时预览将被替换的旧归类，以便确认不会误改分类。
29. 作为用户，我想新建、重命名和删除 GitHub List，以便在整理过程中维护分类体系。
30. 作为用户，我想在删除 List 前看到二次确认，以便避免误删分类集合。
31. 作为用户，我想看到每个 List 的项目总数和待处理数量，以便判断分类积压程度。
32. 作为用户，我想维护“关键词/Topic/语言 → List”的透明规则，以便获得可解释的归类建议。
33. 作为用户，我想看到归类建议命中的字段和目标 List，以便确认规则没有误解项目。
34. 作为用户，我不希望规则命中后自动写回 GitHub，以便保留人工确认权。
35. 作为用户，我不希望未 Star 的自有仓库出现 GitHub List 操作入口，以便工具不偷偷替我新增 Star。
36. 作为用户，我想多选项目并查看即将执行的动作，以便一次处理多个相似项目。
37. 作为用户，我想按动作分组确认批量操作，以便分别确认“取消 Star”和“归类到 List”等不同风险的动作。
38. 作为用户，我不希望仅凭筛选条件就直接执行全部操作，以便避免误操作大批项目。
39. 作为用户，我想在批量执行时看到每个项目的成功或失败结果，以便知道哪些动作真正生效。
40. 作为用户，我想对失败项目单独重试，以便处理权限、限流或仓库状态变化造成的局部失败。
41. 作为用户，我不希望局部失败导致整批操作被假装回滚，以便保留真实的逐项结果。
42. 作为用户，我想撤销本工具本次成功执行的取消 Star，以便在误操作时恢复 Star 关系。
43. 作为用户，我希望撤销前重新检查 GitHub 当前状态，以便不覆盖我在其他地方做出的后续改变。
44. 作为用户，我想仅在 Owned 项目的列表行看到当前适用的 Archive 或 Unarchive，以便快速处理仓库状态。
45. 作为用户，我想删除本人拥有的原始仓库或 fork，以便清理已经不再需要的自有项目。
46. 作为用户，我不希望看到删除他人仓库的入口，以便从产品边界上避免越权和误删。
47. 作为用户，我想在删除前看到完整 `owner/repo`、fork/original、默认分支和最近 commit 等证据，以便确认目标身份。
48. 作为用户，我想通过二次确认并输入完整 `owner/repo` 名称才能删除，以便降低误删概率。
49. 作为用户，我想在删除前留下本地审计记录，以便知道何时、为什么发起过危险动作。
50. 作为用户，我想在删除失败或权限不足时看到原因和重试入口，以便采取下一步修复措施。
51. 作为用户，我不希望删除失败时被静默地从清单移除，以便问题保持可见。
52. 作为用户，我想页面加载时看到上次扫描结果，以便不必每次打开页面都触发网络请求。
53. 作为用户，我想每次扫描都基于最新 GitHub 数据重新生成清单，以便不依赖过期证据。
54. 作为用户，我想看到之前的动作记录，即使相关项目再次命中规则，以便理解重复出现的原因。
55. 作为用户，我想把最近一次扫描结果、List 规则和操作审计保存到一个本地 JSON 文件，以便备份和迁移。
56. 作为用户，我想看到本地 JSON 文件的实际路径，以便检查或复制备份。
57. 作为用户，我不希望本地文件包含 GitHub Token，以便降低凭据泄露风险。
58. 作为用户，我不希望工具保存完整 README、Issue 或 PR 正文，以便减少无必要的本地敏感数据。
59. 作为用户，我想在桌面和小屏幕上都能完成筛选、查看详情和确认操作，以便不被固定屏幕尺寸限制。
60. 作为用户，我想通过文字、图标和状态标签而不只是颜色理解健康信号，以便在可访问性场景下仍能正确判断。

## Implementation Decisions

- **最高测试 seam**：本地 Web 应用的“扫描与动作编排层”。它接收 GitHub 读取/写入适配器提供的数据，输出项目条目、扫描证据、整理建议和逐项动作结果；UI 只通过该 seam 读取状态、提交用户确认的动作。这样可在不连接真实 GitHub 的情况下测试核心行为，也避免前端直接拼装 `gh` 命令。
- **GitHub 适配器**：通过本机 `gh` CLI 调用 GitHub API；负责认证状态检查、分页、速率限制/错误转换以及 Star、Lists、仓库生命周期动作。
- **Web UI 信息架构**：采用表格优先的工作区。表格承担搜索、筛选、多选、关键字段比较与按状态直接展示的单行操作；点击列表行打开详情 Dialog，由 Dialog 承担完整证据和删除等危险动作。项目名称直接链接到对应 GitHub 项目。Lists 是次级导航/筛选维度，不取代表格主工作区。
- **扫描对象**：当前用户已 Star 的仓库，以及当前用户拥有的仓库（包括 fork）。不包含 Watch/Following。
- **扫描证据**：archived/disabled/deprecated、最近 commit、最近 release、近期 issue/PR 活动。阈值默认 12/18/6 个月，并可在页面调整。
- **建议原则**：建议必须引用命中的具体证据；archived/deprecated 只改变优先级，不自动执行写操作；规则未命中时默认进入全部项目视图而非建议处理视图。
- **List 模型**：项目条目至多归类到一个 GitHub List。“归类到 List”会替换已有归类，并在预览中明确说明；“移出 List”会使项目暂未归类。扫描发现远端已有多归类时，不自动改写 GitHub，而是保留一个可见归类并提示用户通过“归类到 List”修正。List 规则是用户可编辑的关键词/Topic/语言映射，建议需展示命中依据。
- **动作模型**：普通动作包括取消 Star、归类到/移出 List；自有仓库额外支持 Archive/Unarchive 和删除原始仓库/fork。单项通过列表行内直接展示的按钮发起，多项通过批量操作栏发起。
- **确认模型**：用户多选后按动作分组预览与确认；每个项目独立执行和记录，不允许无预览的一键全量执行。
- **失败与撤销**：保留逐项成功/失败结果；失败项必须重新生成预览并再次确认后才能执行。取消 Star 的撤销仅针对本次扫描中工具成功执行的动作，并在撤销前重新读取 GitHub 状态。
- **危险动作护栏**：删除放入详情 Dialog 的高级危险操作区域；必须二次确认、展示仓库身份与证据、输入完整 `owner/repo`、先写审计记录。Archive/Unarchive 虽可从 Owned 项目的列表行发起，仍必须经过预览和确认。删除失败不自动重试、不静默移除。
- **本地存储**：单个 JSON 文件保存最近扫描结果、项目关系、List 规则和操作审计；默认位于项目根目录的 `data.json`，也可通过环境变量显式指定其他路径。应用不保存 Token、README/Issue/PR 正文。
- **运行方式**：命令行启动本地服务，浏览器手动访问；页面初始展示上次结果，用户点击后才扫描；不做后台同步、定时任务或实时通知。
- **原型决策来源**：`.scratch/github-organizer/prototype/index.html?variant=B` 验证了表格优先的工作区；A 的证据卡片表达和 C 的 Lists 导航仅作为正式实现的局部设计参考，原型代码不直接进入生产。

## Testing Decisions

- 测试只验证用户可观察行为和 seam 的输入/输出，不锁定具体组件层级、CSS 类名或 CLI 命令拼接细节。
- 首要测试 seam 是扫描与动作编排层，使用假的 GitHub 适配器覆盖正常、局部失败、权限不足、速率限制和状态变化场景。
- 扫描测试应验证：Star/owned/fork 合并去重、分页结果、健康信号阈值、deprecated/archive 优先级、可解释证据和可调整阈值。
- List 测试应验证：归类替换旧归类、远端多归类的修正提示、List 新建/重命名/删除确认、归类规则命中依据以及未 Star 自有仓库禁用 List 操作。
- 批量动作测试应验证：按动作分组预览、逐项成功/失败、局部成功不回滚、失败项重试、取消 Star 撤销的状态检查。
- 危险动作测试应验证：他人仓库不可删除、删除护栏缺一不可、删除前审计记录、失败后保留重试项。
- 本地存储测试应验证：JSON 文件可写入/读取、崩溃或部分写入时不丢失已有记录、文件中不出现 Token 或正文内容。
- UI 测试应优先覆盖键盘可达性、筛选状态保持、列表行打开详情 Dialog、行内只显示状态允许的动作、确认弹窗可取消、错误信息靠近相关项目、移动端不隐藏关键动作。
- 当前仓库没有既有测试或组件库，因此没有可复用的测试先例；正式实现时应先为编排 seam 建立契约测试，再补充 Web 端交互测试。

## Out of Scope

- 云端部署、多设备同步、多人协作和公开 Web 应用。
- Watch/Following 列表整理。
- 自动新增 Star。
- 无预览的筛选后一键全量执行。
- AI 黑箱分类、相似项目/替代项目推荐。
- 语言、许可证、仓库规模等额外元数据管理模块。
- 阅读进度、个人备注、个人主题标签、个人状态字段和“稍后复查”日期。
- 漏洞/依赖安全分析、趋势图、实时通知和后台定时扫描。
- 备份或恢复 GitHub 仓库内容本身。
- 保存完整 README、Issue 或 PR 正文。

## Further Notes

- 当前仓库没有现有应用源码、技术栈、测试或远程 Git 仓库；本规格描述的是从零实现的产品边界。
- GitHub API 的具体 endpoint、权限范围和 List 能力应在实现阶段通过 `gh api` 文档与实际账号权限验证，但不应改变本规格中的人工确认和危险操作边界。
- 单个 JSON 文件优先保证可检查、可备份和无需额外数据库服务；如果未来数据量导致查询困难，应另行提出存储迁移决策，不在首版隐式切换。
- 原型仅用于设计决策，不连接 GitHub；正式实现应重写为可维护的组件和状态管理，而不是直接提升原型代码。
